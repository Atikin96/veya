## 1. What is deployed

* `backend/Dockerfile` — multi-stage build (JDK 21 → JRE 21 Alpine), runs as non-root user `veya`, Spring profile `prod`
  (JSON logs), `HEALTHCHECK` on `/actuator/health/readiness` (ready only after Flyway migrations and a DB connection).
  No secret in the image; build context is the repository root so the contract `docs/api/openapi.yaml` is packaged.
* `infra/docker-compose.yml` — PostgreSQL 17 (role provisioning on first start, port bound to `127.0.0.1` only) and,
  with `--profile app`, the API container (`127.0.0.1:8080` by default).
* `infra/docker-compose.public.yml` + `infra/caddy/Caddyfile` — public override: Caddy reverse proxy with automatic
  HTTPS (Let's Encrypt) on ports 80/443; **no** published ports for PostgreSQL or the API.

## 2. Configuration (environment only — never in Git)

| Variable | Required | Meaning |
|---|---|---|
| `VEYA_POSTGRES_PASSWORD`, `VEYA_OWNER_PASSWORD`, `VEYA_APP_PASSWORD`, `VEYA_READONLY_PASSWORD`, `VEYA_ADMIN_PASSWORD` | yes | database role passwords (`infra/generate-env.sh` creates random values in git-ignored `infra/.env`) |
| `VEYA_JWT_SECRET` | yes | Base64 HMAC key ≥ 32 bytes (generated by the same script); the API refuses to start without it |
| `VEYA_CORS_ALLOWED_ORIGINS` | public: yes | URL(s) of the web client |
| `VEYA_DOMAIN` | public: yes | DNS name of the API for the HTTPS certificate |
| `VEYA_JWT_TTL` (PT60M), `VEYA_BCRYPT_STRENGTH` (12), `VEYA_FOOD_PROVIDER_ENABLED` (false), `VEYA_PLAN_TARGET_TOLERANCE_PCT` (20) | no | tuning |

## 4. Public deployment — recommended option and checklist

Most practical free/low-cost option for this architecture: **one small Linux VM with Docker** (e.g. Oracle Cloud
"Always Free" Ampere VM, or a ~4 €/month VPS) running exactly the verified Compose stack plus the Caddy override.
Managed PaaS (Render, Railway, Fly.io) is possible but needs extra work: their managed PostgreSQL does not allow the
cluster-level role provisioning of `infra/postgres/initdb/01-create-roles.sh` (non-superuser `veya_owner` / `veya_app`
split), which the database criterion relies on.

Manual actions required (need the account owner; not possible from this session):

1. Create the VM (Ubuntu 24.04), open inbound TCP 22, 80, 443 only.
2. Point a DNS name (e.g. `veya-api.<your-domain>`, or a free DuckDNS name) to the VM's public IP.
3. On the VM:
   ```bash
   sudo apt-get update && sudo apt-get install -y docker.io docker-compose-v2 git
   git clone https://github.com/Atikin96/veya.git && cd veya
   sh infra/generate-env.sh                                   # random secrets, stay on the server
   export VEYA_DOMAIN=veya-api.<your-domain> VEYA_CORS_ALLOWED_ORIGINS=https://<web-client-url>
   sudo -E docker compose -f infra/docker-compose.yml -f infra/docker-compose.public.yml --profile app up -d --build
   ```
4. Verify **from another machine** (outside the VM):
   ```powershell
   curl.exe -i https://veya-api.<your-domain>/actuator/health/readiness      # 200 {"status":"UP"}
   curl.exe -i https://veya-api.<your-domain>/api/v1/me                      # 401 application/problem+json
   powershell -ExecutionPolicy Bypass -File infra\smoke\smoke-test.ps1 -BaseUrl https://veya-api.<your-domain>
   Test-NetConnection veya-api.<your-domain> -Port 5432                      # must FAIL (database not public)
   ```
5. Record the public URL and the outputs in the submission.
